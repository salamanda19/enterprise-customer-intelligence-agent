# Writeup：有依據的綜合度假村客戶智慧分析代理

## 問題

綜合度假村（IR）的「客戶問題」看起來像一般 BI 問答，實際上踩在三道容易被 LLM 踩穿的邊界上：（1）**語意歧義**——「酒店營收」是淨房收還是支柱合計？（2）**資料權利缺口**——租戶商場 GMV 不在 IR 事實表裡，模型卻很會「估計」；（3）**政策**——因果、逐客 PII、範圍外指標（RevPAR）不該用流利散文蒙混。本專案刻意做一個**可驗證**的代理：數字來自凍結合成庫上的命名指標，拒絕與降級來自政策閘，而不是模型記憶。

讀者是招聘主管與技術面試官，不是終端產品用戶。因此交付物是可重現的契約、金標、評測與失敗分析，而不是聊天 Demo 的臨場感。

## 語意層與業務約束

語意 YAML 鎖定客戶＝會員、活躍＝90 天內 IR 錢包現金、VIP＝Tier 3（最高等級）、高價值＝12 個月錢包現金門檻（凍結後鎖為 900）。F&B／零售營收預設僅自營；酒店預設支柱合計並**聲明**。購物禮券核銷≠商場 GMV≠IR 零售營收。套裝中租戶早餐與購物禮券走負債事件，不進該支柱營收；自營掛房帳晚餐歸 F&B。這些規則寫進 SSOT 與不變量測試，避免「產生器碰巧對、代理卻另說一套」。

核准文件可引用，但若與語意層互斥（例如把 VIP 寫成飯店名單），系統必須 `DEFINITION_CONFLICT` **拒絕選邊**——這是刻意與「RAG 永遠蓋過系統提示」相反的設計。

## 驗證策略

金標金額**禁止手填**：`golden runner` 對凍結 DuckDB 算出 `figures[]`，寫入 `eval/goldens/`。代理評測自動比對 `response_mode`、原因碼、數字與禁止主張字串；行為門檻預先登記為模式／原因碼 100%、禁止主張 0、數字 100%。Q5 必須是**真降級**（可觀察自營零售 ∪ 禮券核銷 + `COVERAGE_GAP`），不是空拒絕。Q6／Q7／Q13／RevPAR 在 pre-flight 攔截。驗證器要求解釋不得引入 `figures[]` 沒有的新數（Q11／Q12 有負向測）。

另設 offline naive baseline（少工具 RAG＋發明數字；可選 live LLM）：並列結果、不預填優勝。首次全量後，生成性指標（有依據、解釋品質、相對差距、延遲／成本）才寫進評測文件，且**不得**回放寬行為門檻。

## 拒絕與降級為什麼比「答得出來」更重要

面試官常問：你怎麼證明系統不會亂編？本專案的答案是契約化行為：

- **拒絕**：估計租戶真實消費、因果增量、逐客 PII、RevPAR／ADR。
- **降級**：商場花費 → 可觀察子集並聲明租戶實付未知。
- **聲明後作答**：酒店營收、客戶數、禮券是否等於營收。

原因碼可機器比對；`ACCESS_RESTRICTED` 刻意不存在——這不是 IAM Demo。提示注入樣本只能當資料，不能改系統指令。

## 取捨

- **確定性優先於 LLM**：弱機、無 GPU、CI 不燒 token；實稱數字走命名指標，自由 SQL 僅探索。
- **合成世界而非真實 IR**：可重建、可公開；代價是外部效度有限，必須在 writeup 承認。
- **單代理編排**：未證明準確度瓶頸前不做多代理；失敗分析先寫。
- **V3 包裝薄**：FastAPI + Docker + CI + 示範腳本；精緻產品 UI／K8s／IAM 不做（本機 Explore 為可選 I8）。

## 失敗與局限

Naive baseline 在 Q5–Q7、Q13、衝突 VIP 上系統性失敗（發明 GMV、肯定因果、輸出假 PII、衝突選邊），對照出政策閘與金標的價值。Agent 路徑本輪行為門檻全過，但若日後關閉 `deterministic_first` 接上生成模型，幻覺類失敗可能重現——那時應新開評測輪次，而不是放寬契約。變體題約 58 題（換期、換等級、對抗措辭），未衝到 100；時間盒內以 Q1–Q15 全覆蓋加有限變體為準。

局限：無真實租戶 POS、無線上實驗設計、無生產 IAM；延遲與成本以本地 DuckDB／零 token 為主。作品集主張是「會拒絕、會降級、數字可重算」，不是「什麼都答得出來」。
