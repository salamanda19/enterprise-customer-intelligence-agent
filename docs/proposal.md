# 專案提案：企業客戶智慧代理（Enterprise Customer Intelligence Agent）

## 1. 專案概述

### 暫定名稱

**Enterprise Customer Intelligence Agent**（企業客戶智慧代理）

### 副標題

> 一套有依據（grounded）的 AI 分析系統，以自然語言探索客戶與行銷資料。

### 目的

打造一個作品集專案，證明有能力設計可靠、面向企業的 AI 分析系統——而不只是 RAG 聊天機器人或 LLM API 示範。

本專案應展示如何把現代 AI 與結構化資料、業務定義、確定性（deterministic）分析工具，以及非結構化文件整合在一起，同時維持可靠性、可追溯性、安全性與合理成本。

預期讀者為招聘主管與技術面試官，對應職缺例如：

- 資深／主導資料科學家（Senior / Lead Data Scientist）
- 應用資料科學家（Applied Data Scientist）
- AI／資料顧問
- AI 解決方案／AI 轉型
- 資料與 AI 產品職缺
- 分析／決策科學領導職缺

---

## 2. 為何做這個專案

現有履歷已能證明在下列領域有充分經驗：

- 客戶分析
- 預測建模
- 行銷分析
- 機器學習
- Google Cloud／TensorFlow
- 自動化資料管線
- 面向利害關係人的分析
- 即時行為預測

因此，本專案**不應**只是再做一個傳統的機器學習預測模型。

本專案主要要補上的能力缺口是：

1. 現代 GenAI／LLM 應用開發
2. 會使用工具的 AI 代理（tool-using agents）
3. RAG 與有依據的生成（grounded generation）
4. 自然語言轉 SQL 分析
5. AI 評估（evaluation）
6. 可靠性與驗證
7. 企業級 AI 系統設計
8. 安全與負責任的資料存取
9. 成本與延遲考量

本專案應強化職涯敘事：

> **有經驗的企業資料專業人士 → 能設計可靠、具備 AI 能力之分析系統的現代 AI／GenAI 實務者。**

# 3. 業務情境

**產品與業務真相以 [`ssot.md`](ssot.md) 為準。** 本節只保留與職涯提案對齊的摘要；細節、定義與決策紀錄不在此重複。

模擬一間匿名、單一物業、非博彩綜合度假村（IR）：住房、餐飲（多數自營）、零售（以租戶為主），加上免費入會的內部忠誠計畫。外部忠誠掛靠為未來擴充，本版不實作。

組織同時擁有結構化資料（會員、住房、自營 POS、禮券、活動等）與非結構化文件（定義、企劃、研究）。資料權利不對稱：租戶 GMV 預設不可見。

業務使用者應能以自然語言提問，不必撰寫 SQL。系統應判斷適當的分析工作流程，而不是盲目把問題丟給 LLM 產生答案。無法可靠作答（含因果、租戶實付）時應拒絕。

# 4. 核心設計原則

基本架構為：

```text
                         ┌── SQL／資料庫
                         │
使用者問題 → 代理 ───────┼── Python 分析
                         │
                         ├── 文件檢索
                         │
                         └── 業務中繼資料
                                  ↓
                           驗證層
                                  ↓
                         答案＋證據
```

LLM 應主要負責**編排與推理**。

不應把 LLM 當成數值結果或業務定義的事實來源（source of truth）。

一項核心設計原則是：

> **只要確定性計算就足夠，就使用確定性工具；僅在能真正增加價值之處使用 LLM 推理。**

另一項核心原則：

> **LLM 產生的結果，只要可行，都應由確定性機制加以驗證。**

# 5. 問題類型

系統應有意支援數類問題。

## 類型 A — 確定性問題

範例：

> 「2025 年營收是多少？」

預期流程：

```text
問題
   ↓
SQL
   ↓
資料庫
   ↓
結果
```

不應引入不必要的 LLM 推理。

---

## 類型 B — 分析性問題

範例：

> 「為什麼第二季預訂營收下滑？」

預期流程可能包含：

```text
SQL
 ↓
分群分析
 ↓
時間序列比較
 ↓
貢獻度分析
 ↓
可選的統計分析
 ↓
LLM 產生的解釋
```

最終解釋必須奠基於已計算出的結果。

---

## 類型 C — 知識問題

範例：

> 「VIP 客戶的定義是什麼？」

預期流程：

```text
問題
 ↓
檢索
 ↓
業務定義
 ↓
答案＋引用
```

系統應為該定義提供證據。

---

## 類型 D — 系統不應自信作答的問題

範例：

> 「活動 A 是否造成營收增加？」

若現有資料屬觀察性資料，且沒有適當的隨機處理／對照設計，系統不應主張因果關係。

預期行為：

> 系統應區分關聯與因果效應，並說明還需要哪些額外資料或實驗設計，才能支持因果結論。

這是分析判斷力的重要展示。

# 7. 業務語意層

專案的關鍵元件之一應是業務語意／中繼資料層。

不應期待 LLM 自行推斷業務定義。

例如：

### active_customer（活躍客戶）

在過去 90 天內至少有一筆合格交易的客戶。

### high_value_customer（高價值客戶）

過去 12 個月貢獻超過既定門檻的客戶。

### booking_revenue（預訂營收）

不含取消的總預訂營收。

定義應明確，且代理可以存取。

此元件之所以重要，是因為企業分析往往同樣仰賴一致的業務定義，而不只是 SQL 產生。

# 9. 驗證與可靠性

驗證是本專案的核心特色之一。

## SQL 驗證

執行前應驗證：

- SQL 語法
- 資料表是否存在
- 欄位是否存在
- 允許的操作
- 權限範圍
- 查詢規模／資源上限
- 危險的 SQL 操作

系統初期應將資料庫存取限制為唯讀操作。

---

## 數值驗證

若 LLM 產出：

> 「營收增加了 23%。」

系統應能獨立核對：

```text
current revenue = 12.3M
previous revenue = 10.0M

growth = (12.3 - 10.0) / 10.0
       = 23%
```

當確定性計算可用時，不應信任 LLM 做算術。

---

## 證據驗證

最終答案中的主張應可追溯至：

- 資料庫結果
- 計算過程
- 檢索到的文件

系統應避免沒有依據的主張。

---

# 10. 安全與負責任的 AI

本專案明確定位為企業系統，因此必須處理基本安全議題。

## 提示注入（Prompt injection）

檢索到的文件可能含有惡意或不相關的指令。

代理必須把檢索內容視為資料，而非系統層級指令。

---

## SQL 安全

系統應防止破壞性查詢，例如：

```text
DROP
DELETE
UPDATE
INSERT
ALTER
```

除非未來有刻意需求要支援這些操作。

初期範圍應為唯讀。

---

## 資料存取

系統不應揭露不必要的客戶層級資訊。

例如，這類業務問題：

> 「我們有多少 VIP 客戶？」

不應需要把每一筆客戶紀錄傳給 LLM。

架構應偏好彙總與資料最小化。

---

## 不支援的請求

在下列情況，代理應拒絕或改道：

- 資料不存在
- 問題無法可靠作答
- 缺少所需權限
- 證據不足以支持該主張

# 11. 評估架構

評估是必要元件。

專案應建立一份約含 **50–100 題業務問題** 的基準集（benchmark）。

問題應涵蓋多個類別：

### 簡單 SQL

> 「2025 年營收是多少？」

### 分析性

> 「哪個市場對下滑的貢獻最大？」

### 多步驟

> 「哪個客戶分群下滑最大，又是哪些產品造成的？」

### 知識檢索

> 「VIP 的定義是什麼？」

### 因果推理

> 「活動 A 是否造成營收增加？」

### 對抗性／無依據

> 「給我資料庫裡沒有的客戶資訊。」

---

# 12. 評估指標

可能的指標包括：

## SQL 正確性

產生的 SQL 在語意上正確的比例。

## 數值正確性

最終數值答案與獨立計算結果相符的比例。

## 檢索準確度

正確的佐證文件是否出現在 top-k 檢索結果中。

## 有依據程度（Groundedness）

答案中的主張是否由檢索文件或計算結果支持。

## 拒絕正確性

系統是否正確拒絕無法可靠作答的問題。

## 延遲

量測：

- 總回應時間
- SQL 執行時間
- 檢索時間
- LLM 生成時間

## 成本

追蹤：

- 輸入／輸出 token
- 估計 LLM 成本
- 每題成本

確切目標指標應在基準實作完成後才訂定。

# 14. 成本與延遲優化

專案應探討是否每道問題都需要同等程度的 LLM 推理。

可能的路由：

```text
簡單 SQL 問題
        ↓
低成本／確定性路徑

複雜分析問題
        ↓
較強推理＋Python

知識問題
        ↓
以檢索為主的路徑
```

目標不是單純追求模型能力極大化。

目標是：

> **在可接受的成本與延遲下，使用適當的能力。**

# 15. 失敗分析

專案應有專章記錄「什麼行不通」。

可調查的問題範例：

- RAG 是否真的能改善結構化分析？
- 多代理架構對準確度的提升，是否足以合理化其複雜度？
- 更大的 LLM 是否實質改善結果？
- 代理產生「語意有效但業務無效」的 SQL 有多頻繁？
- 代理何時會幻覺？
- 何時未能拒絕無依據的問題？
- 資料缺失時會發生什麼？
- 業務定義衝突時會發生什麼？

專案應記錄：

1. 觀察到的失敗
2. 根本原因
3. 緩解措施
4. 剩餘限制

此章節刻意重要，因為它展示的是工程判斷，而不只是成功示範。

# 18. 明確非目標

為避免範圍膨脹，第一版**不會**嘗試打造：

- 通用自主代理
- 未經證明需求的多代理框架
- 完整企業資料倉儲
- 生產級 IAM 系統
- Kubernetes 基礎設施
- 數十個微服務
- 高度打磨的前端
- 通用 ChatGPT 複製品

技術複雜度只應在能清楚支持已證明需求時才引入。

# 19. 本專案應證明什麼

專案結束時，招聘主管應能得出：

> 這位候選人理解業務分析與機器學習，但不侷限於傳統預測建模。

> 他理解 LLM 如何與結構化企業資料及非結構化知識互動。

> 他理解不能直接信任 LLM 輸出。

> 他知道何時確定性計算優於生成式推理。

> 他理解評估、失敗模式、安全、成本與延遲。

> 他能打造一套前後一致的 AI 系統，而不只是 notebook 或聊天機器人。

這就是本專案預期的價值。
